## What it does

1. **Widget.** A small frameless, always-on-top window shows live SpO₂, heart rate and how fresh the data is.
2. **Amber alert.** When SpO₂ drops below the account's "Oxygen amber below" setting, the non-primary monitor flashes orange.
3. **Red alert.** Below "Oxygen red below", it flashes red and an alarm sound loops.
4. **Snooze.** Clicking the overlay, the widget's button or the tray item silences the alert for 15 s. If SpO₂ is still low after that, the alert returns. If amber escalates to red, the snooze is cancelled.
5. **Tray.** Closing the dashboard hides it to the tray. Data collection, the widget and alerts keep running. Quit is only in the tray menu.

## Architecture in one paragraph

The Python sidecar decides the alert level and holds the snooze, so the widget, overlay and tray always agree. The poller feeds every reading to an in-memory state machine. A Rust thread in the Tauri shell polls `GET /api/alert-state` every 2 s. It shows or hides the overlay, starts or stops the sound with `PlaySoundW`, and updates the tray tooltip. The widget is a webview on `http://127.0.0.1:8877/widget` that polls the same endpoint. The overlay is a bundled local page (`overlay.html`). Rust pushes state to it.

## Alert engine rules (`app/alerts.py`)

| Constant | Value | Meaning |
|---|---|---|
| `ENTER_READINGS` | 2 | Consecutive distinct readings needed to enter a level |
| `EXIT_READINGS` | 2 | Consecutive distinct readings needed to leave a level |
| `HYSTERESIS` | 1 | To leave a level, SpO₂ must reach threshold + 1 |
| `STALE_SECONDS` | 60 | No new reading for this long means the device is stale |
| `SNOOZE_SECONDS` | 15 | Snooze length |

- **Repeats.** A reading whose `recorded_at` matches the previous one is ignored. It also doesn't refresh freshness.
- **Offline readings.** If the sock is off or disconnected, or SpO₂ or heart rate is ≤ 0 (`is_offline_reading`), the level is `none` and the streak counters reset.
- **Owlet's own flags** act immediately. `CRIT_OX_ALRT` or `critical_oxygen_alert` gives red. `LOW_OX_ALRT` or `low_oxygen_alert` gives amber.
- **Red counts as amber.** A red reading also counts toward the amber streak.
- **Leaving red.** Red drops to `none` if the amber exit condition is also met; otherwise it drops to amber.
- **At the threshold.** A reading exactly at the threshold holds the current level.
- **Stale devices** report `none` and don't count toward the overall level.
- **Snooze checks** happen when `state()` runs. The snooze is cleared if it has expired, if the level has risen above the snoozed level, or if the level is now `none`. That last case stops a snooze from carrying over to the next real alert.
- **Snoozing with nothing alerting** returns `snoozed_until: null` and stores nothing.

## Deviations from the plan

1. **`tauri-plugin-single-instance` added.** It isn't in the plan. Because closing now hides to the tray, launching again from the Start Menu would otherwise start a second copy with its own tray, widget and alarm thread. A second launch now shows the first copy's dashboard.
2. **No `ureq`.** `http_json()` in `main.rs` is a small std-only HTTP/1.0 client. It uses `Connection: close`, which keeps the response un-chunked. It's localhost only.
3. **The stale timeout scales with the poll interval.** It's `max(60, 2 × interval + 15)`, computed in `Poller._feed_alerts`. Accounts can be set to poll every 300 s, and a flat 60 s would mark them stale permanently.
4. **New `overlay_state` command.** The overlay page calls it when it loads, so it can't miss the first state event while still loading.
5. **Window calls run directly from the alert thread,** not through `run_on_main_thread`. Tauri window methods already hand the call to the main thread. The overlay is only ever created from the alert thread, never on the main thread, which avoids the known WebView2 deadlock when a window is created inside a sync command.
6. **Stopping the sound** uses `PlaySoundW(NULL, None, SND_FLAGS(0))`, not `SND_PURGE`, which is documented as unsupported on modern Windows.
7. **`ENTER_READINGS` stays at 2 for red.** In the local database the median gap between readings is 10 s (p10 10 s, p90 11 s). That's right at the plan's "drop to 1 if slower than about 10 s" line, so I left it unchanged. As a result red fires roughly 10–20 s after Owlet reports the drop.

## Where review is most useful

1. **State-machine correctness** (`DeviceAlertTracker.observe`):
   - the streak counters across level changes
   - whether red → amber → none can stall
   - the interaction between an Owlet flag and the threshold streaks
   - whether the `reason` field stays accurate
2. **Snooze semantics** (`AlertMonitor.state`/`snooze`):
   - The snooze is global but `level` is calculated for each user's scope. That's fine for the single-user desktop app; check that it's acceptable for hosted multi-user mode.
   - `state()` changes snooze and test state as a side effect of a GET.
3. **Concurrency in `main.rs`:**
   - the `Shell.applied` mutex race between `do_snooze` (command or tray thread) and `apply_state` (alert thread)
   - `ALARM_ON` ordering
   - whether a failed snooze POST correctly lets the alert come back on the next poll (`applied` is cleared to force a re-apply)
4. **Security and capabilities:**
   - the widget window now has IPC access through the `127.0.0.1:8877` remote scope
   - check that the overlay capability is minimal
   - `/api/alert/test` and `/api/alert/snooze` are POSTs without CSRF tokens; check whether that matches how the rest of the app's POST routes behave
5. **`http_json` robustness:** partial reads, non-200 statuses, and a body parse that relies on `\r\n\r\n` splitting.
6. **Lifecycle:**
   - The removed `WindowEvent::Destroyed` → `kill_sidecar` handler. Shutdown now depends only on `RunEvent::Exit`.
   - `CloseRequested` is now always prevented for every window. Check that this can't trap the app, for example during an installer upgrade. The NSIS pre-install hook kills the processes.
7. **Widget page:** the `esc()` escaping of account names in `innerHTML`, and the timer and failure handling.

## Known limitations, accepted in the plan

- **Not a medical alarm.** It depends on the Owlet cloud, the internet connection, this PC being awake, and Windows audio volume. The Owlet base station stays the primary alarm.
- **Remote-server mode.** Alerts only work while this PC collects the data. In remote mode the widget says alerts are unavailable.
- **Exclusive full-screen apps** can draw over the overlay on the same monitor.
